# Рефакторинг: снятие искусственных ограничений

Цель — убрать хардкод-лимиты, лишние фолбеки, и подготовить код к многопоточности.
Многопоточность сейчас НЕ реализуется — но код не должен ей мешать.

---

## 1. Фиксированные таблицы -> динамические

### 1.1 VmaTable: `[Option<Vma>; 256]` -> `Vec<Vma>`

**Файл:** `sumi-kernel/src/memory/vma.rs`

**Проблема:** Лимит 256 VMA. Динамический линкер с десятком .so легко генерит 100+ маппингов. Сложная программа упрётся.

**Решение:** Заменить на `Vec<Vma>` (через `#[global_allocator]`). Линейный поиск оставить — при N < 10000 он быстрее дерева из-за кэш-локальности. `remove_overlapping` возвращает `Vec<Vma>` вместо `[Option<Vma>; 4]`.

**Инициализация:** `VmaTable::new()` вместо `const fn`, создаётся в `_start()` после инициализации аллокатора.

### 1.2 FdTable: `[Option<FileDescriptor>; 256]` -> `Vec<Option<FileDescriptor>>`

**Файл:** `sumi-kernel/src/fs/mod.rs`

**Проблема:** Лимит 256 fd. Серверные приложения с сокетами могут открывать тысячи.

**Решение:** `Vec<Option<FileDescriptor>>`, начальный размер 64, растёт при необходимости. `alloc()` ищет первый `None`; если не нашёл — делает `push(Some(desc))`.

### 1.3 KernelAllocator active table: `[ActiveAllocation; 4096]` -> `Vec<ActiveAllocation>` или убрать

**Файл:** `sumi-kernel/src/memory/alloc/kmalloc.rs`

**Проблема:** Жёсткий лимит 4096 одновременных аллокаций. С ростом использования Box/Vec для внутренних структур ядра этот лимит станет узким.

**Решение:** Вариант A (простой) — увеличить до 16384 и оставить массив. Вариант B (правильный) — убрать active-tracking целиком, хранить размер аллокации в хедере перед возвращаемым указателем (как malloc). Это снимает лимит и убирает O(n) поиск при free(). Предпочтительный вариант — B.

## 2. Убрать лишние фолбеки

### 2.1 VIRTIO_FS: `spin::Once` -> прямая инициализация

**Файлы:** `sumi-kernel/src/lib.rs`, `kernel_main.rs`, все `syscall/handlers/*.rs`

**Проблема:** `VIRTIO_FS` объявлен как `spin::Once<VirtioFsClient>`, и каждый syscall-хендлер делает `match crate::VIRTIO_FS.get() { Some(fs) => ..., None => return EIO }`. Это 15+ мест с бесполезной проверкой — virtio-fs всегда есть.

**Решение:** Инициализировать в `_start()`, хранить как глобальную ссылку (например `static VIRTIO_FS: spin::Once<...>` оставить, но паниковать при отсутствии вместо EIO). Добавить хелпер `fn fs() -> &'static VirtioFsClient` который делает `.get().unwrap()` (или `expect`). Заменить все `match VIRTIO_FS.get()` на вызов хелпера.

### 2.2 VIRTIO_CONSOLE: убрать debugcon-фолбек

**Файл:** `sumi-kernel/src/syscall/handlers/io.rs`

**Проблема:** `console_write()` проверяет `VIRTIO_CONSOLE.get()` и фолбечит на `debugcon_write_byte()`. Консоль всегда есть.

**Решение:** Аналогично — хелпер `fn console() -> &'static VirtioConsole`, паника при отсутствии.

### 2.3 DAX fallback в mmap

**Файл:** `sumi-kernel/src/syscall/handlers/memory.rs`, строки 148-160

**Проблема:** Когда DAX-слоты кончаются, `dax_path()` возвращает `Err(())` и mmap фолбечит на `private_copy_path()` — аллоцирует физические страницы и читает файл через FUSE_READ. Это медленный путь, который маскирует исчерпание DAX-окна.

**Решение:** Оставить. Это не "фолбек для отсутствующего устройства", а валидная стратегия управления ресурсами. DAX-окно конечно (128GB), и файлов может быть больше. Private copy — корректный путь.

## 3. Подготовка к многопоточности (без реализации тредов)

### 3.1 Syscall stack: `static mut SYSCALL_STACK` -> per-CPU

**Файл:** `sumi-kernel/src/arch/x86_64/syscall.rs`

**Проблема:** Один глобальный syscall-стек и `static mut SAVED_USER_RSP`. При двух vCPU, выполняющих syscall одновременно — порча стека и потеря RSP.

**Решение (сейчас):** Не трогать — один vCPU. Но добавить `// TODO: per-vCPU syscall stack when adding SMP` комментарий. Структура для будущего: массив стеков, индексируемый по CPU ID (из GS base или APIC ID).

### 3.2 Page table: нет синхронизации

**Файл:** `sumi-kernel/src/arch/x86_64/pagetable.rs`

**Проблема:** `map_2mb()` и `unmap_2mb()` мутируют page table entries без блокировки. TOCTOU: два потока проверяют `is_present()`, оба проходят, оба пишут.

**Решение (сейчас):** Обернуть `RootPageTable` в `spin::Mutex` по аналогии с остальными глобалами. Да, это грубая блокировка, но она корректна и не добавляет overhead на одном vCPU (uncontended lock — 1 atomic op). В будущем можно перейти на per-entry locking.

### 3.3 MMAP_NEXT: lock gap

**Файл:** `sumi-kernel/src/syscall/handlers/memory.rs`, строки 62-73

**Проблема:** `MMAP_NEXT` лочится для резервирования адреса, потом лок отпускается, потом идёт маппинг. Два потока могут получить разные адреса (это ок), но rollback при ошибке не атомарен с резервированием.

**Решение (сейчас):** Допустимо — один vCPU. Добавить комментарий: `// NOTE: address reservation is not atomic with mapping — requires revisiting for SMP`.

### 3.4 FD_TABLE offset TOCTOU

**Файл:** `sumi-kernel/src/syscall/handlers/io.rs`

**Проблема:** `sys_read()` берёт offset из FD_TABLE, отпускает лок, делает I/O, снова берёт лок и обновляет offset. Между этим другой поток может закрыть/переоткрыть fd.

**Решение (сейчас):** Допустимо — один vCPU. Для будущего: вынести offset в отдельный `Arc<AtomicU64>` per-fd, или держать лок на время I/O (что блокирует другие fd — плохо), или использовать per-fd mutex.

## 5. Что НЕ трогаем

- **PageAllocator bitmap** (`[u64; 16384]`) — это статический битмап для 2TB RAM, его размер определяется железом, а не количеством аллокаций. Динамический не нужен.
- **DaxAllocator bitmap** (`[u64; 1024]`) — аналогично, размер окна фиксирован хостом.
- **Virtqueue ring sizes** (`QUEUE_SIZE = 256`) — это virtio spec, менять нельзя.
- **Syscall stack** — один vCPU, менять рано.
- **DAX fallback на private copy** — валидная стратегия, не лишний фолбек.
